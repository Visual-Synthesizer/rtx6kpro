# CUTLASS DSL 4.6 SM120 W4A16 Prefill Regression

This page records a performance regression found while rebasing the unified
GLM-5.2/DS4 image onto the July 2026 Gilded Gnosis source stack. It also records
an unrelated packaging trap that initially made the CUTLASS DSL 4.5.2 control
look incompatible.

The validated release decision is:

- keep the rebased CUTLASS C++ source used to build FlashInfer;
- pin the runtime CuTe DSL packages to `4.5.3`;
- install `nvidia-cutlass-dsl-libs-cu13` last;
- do not carry the experimental B12X route-block workaround.

The issue is specific to generated SM120 B12X W4A16 MoE code observed here. It
is not evidence that every CUTLASS DSL 4.6 kernel is slower.

## Test Scope

The controlled comparison used:

| Item | Value |
|---|---|
| GPUs | 8x RTX PRO 6000 Blackwell per server |
| Model | `lukealonso/GLM-5.2-NVFP4` |
| Parallelism | TP8, DCP1 |
| Speculative decode | MTP off |
| MoE mode | A16, B12X W4A16 fused MoE |
| KV cache | `fp8_ds_mla` |
| Loader | InstantTensor `BUFFERED` |
| vLLM | Gilded Gnosis v19 integration source `2152d08149d097c077d59fb3c9fde2ad7af525fb` |
| B12X | `bc85ef36192cb6e444d42ba7be86e1e125cca98a` |
| FlashInfer | `801d57a08958c13d375ddbb6be3be4808f48a708` |
| CUDA / PyTorch | CUDA 13.2.1, PyTorch `2.12.0+cu132` |

Both paired models were fully ready before either benchmark client started.
Each case used a correctness request, one decode measurement, one discarded
64k prefill warmup, and three measured 64k prefill runs.

## Symptom

CUTLASS DSL 4.6.0 left CC1 decode unchanged but reduced 64k prefill by about
14.4-14.5%. Reverting only the runtime DSL packages restored performance.

| Case | DSL | Decode CC1 tok/s | Prefill 64k runs tok/s | Median tok/s |
|---|---:|---:|---|---:|
| A16 original | 4.6.0 | 87.364 | 5,053 / 5,052 / 5,051 | 5,052 |
| A16 original | 4.5.2 | 87.033 | 5,913 / 5,907 / 5,908 | 5,908 |
| A16 original | 4.5.3 | 87.180 | 5,912 / 5,909 / 5,906 | 5,909 |
| A16 online MXFP8 | 4.6.0 | 92.642 | 5,066 / 5,060 / 5,056 | 5,060 |
| A16 online MXFP8 | 4.5.2 | 92.376 | 5,925 / 5,919 / 5,916 | 5,919 |
| A16 online MXFP8 | 4.5.3 | 92.181 | 5,915 / 5,909 / 5,907 | 5,909 |

For the original A16 case, 4.6.0 is 14.50% slower than 4.5.3. Expressed in
the other direction, 4.5.3 restores 16.96% throughput over 4.6.0. The online
MXFP8 case shows the same effect because its expert weights and A16 expert
compute remain on the same B12X W4A16 path.

## Root Cause Evidence

A short rank-0 Torch profiler capture isolated the additional GPU time to the
prefill signature of `b12x.moe.fused.w4a16.kernel.W4A16FusedMoeKernel`. The
affected kernel was approximately 2.02x slower per launch under DSL 4.6.0.
Sparse-MLA attention and indexer kernels did not show the corresponding delta.

The generated cubins explain the kernel-level change:

| CuTe DSL | Registers/thread | Stack bytes/thread | Shared bytes | Constant bytes |
|---|---:|---:|---:|---:|
| 4.5.2 / 4.5.3 | 242 | 0 | 1,024 | 1,068 |
| 4.6.0 | 255 | 256 | 1,024 | 1,068 |

`cuobjdump --dump-resource-usage` output for 4.5.x:

```text
Function kernel_cutlass_kernel_b12xmoefusedw4a16kernelW4A16FusedMoeKernel...:
 REG:242 STACK:0 SHARED:1024 LOCAL:0 CONSTANT[0]:1068
```

The same signature generated by 4.6.0:

```text
Function kernel_cutlass_kernel_b12xmoefusedw4a16kernelW4A16FusedMoeKernel...:
 REG:255 STACK:256 SHARED:1024 LOCAL:0 CONSTANT[0]:1068
```

The compiler reaches the SM120 register ceiling and emits per-thread stack
traffic. This is the confirmed mechanism behind the observed slowdown. The
internal compiler change that causes the poorer allocation was not patched;
the tested fix is the runtime compiler pin.

Upstream vLLM adopted CUTLASS DSL 4.6.0 in
[PR #47442](https://github.com/vllm-project/vllm/pull/47442), represented in
the rebased source by commit `7cd1d57b74`. That dependency update is valid for
upstream generally, but this B12X SM120 signature requires a regression gate.

## Rejected Workaround

An experimental B12X route-block cap partly reduced register pressure under
4.6.0:

| Route-block cap | Decode CC1 tok/s | Prefill 64k runs tok/s | Median tok/s |
|---:|---:|---|---:|
| 48 | 87.246 | 5,560 / 5,856 / 5,853 | 5,853 |
| 32 | 86.054 | 5,613 / 5,603 / 5,600 | 5,603 |

This was useful to confirm sensitivity to generated-kernel shape, but it is
not the release fix. Cap 48 retained a cold outlier and remained below the
clean 4.5.x result; cap 32 also reduced decode. No route-block patch is carried
in v19.

## Packaging Trap

`nvidia-cutlass-dsl-libs-base` and `nvidia-cutlass-dsl-libs-cu13` 4.5.x ship
overlapping Python paths. Installing both in one unconstrained transaction can
leave the base copy of `cutlass/cute/nvgpu/warp/mma.py` on disk even though
package metadata reports that the CU13 wheel is installed.

Observed files:

| Installation | Bytes | SHA-256 | `MmaMXF8Op` |
|---|---:|---|---|
| 4.5.2/4.5.3 CU13 file | 21,445 | `cccf48864bae9554acdf708fd66a7b2fe729948ca3768205df3e251c8dc71fd2` | yes |
| Incorrect 4.5.2 base file | 15,051 | `3febd26c2c40...` | no |
| 4.6.0 CU13 file | 27,244 | `b305d518aabdf251d6a7af044968044d53b56ba76ad909c74f5c14e8fd0c67d4` | yes |

The first 4.5.2 diagnostic failed in the sparse indexer because this incorrect
base file lacked `MmaMXF8Op`. That failure was not a vLLM source incompatibility
and is not evidence against 4.5.x.

The reliable install order is:

```bash
python -m pip install --no-deps \
  nvidia-cutlass-dsl==4.5.3 \
  nvidia-cutlass-dsl-libs-base==4.5.3
python -m pip install --force-reinstall --no-deps \
  nvidia-cutlass-dsl-libs-cu13==4.5.3
```

The v19 build repeats the CU13 reinstall after all runtime dependency changes
and asserts package versions, `MmaMXF8Op`, and the full file hash.

## Reproduce The A/B Test

The parameterized overlay is stored at
[`cutlass-dsl-46-w4a16-regression-2026-07-18/Dockerfile`](cutlass-dsl-46-w4a16-regression-2026-07-18/Dockerfile).
Build both variants from the same base image:

```bash
docker build \
  -f models/glm5.2/cutlass-dsl-46-w4a16-regression-2026-07-18/Dockerfile \
  --build-arg CUTLASS_DSL_VERSION=4.5.3 \
  -t local/glm52-v19-cutlass453 .

docker build \
  -f models/glm5.2/cutlass-dsl-46-w4a16-regression-2026-07-18/Dockerfile \
  --build-arg CUTLASS_DSL_VERSION=4.6.0 \
  -t local/glm52-v19-cutlass460 .
```

Use a fresh cache root for every compiler version. Reusing a B12X CuTe cache
would compare cached cubins rather than compilers.

```bash
IMAGE=local/glm52-v19-cutlass453 \
RESULT_ROOT=/root/bench-results/glm52-v19-cutlass453-repro \
CACHE_A=/root/.cache/glm52-cutlass453/slot-a \
CACHE_B=/root/.cache/glm52-cutlass453/slot-b \
TMP_ROOT=/root/vllm/tmp/glm52-cutlass453 \
SETTLE_SECONDS=30 PREFILL_REPEATS=3 FORCE_RERUN=1 \
./scripts/bench-glm52-v19-validation.sh configs \
  'nvfp4-a16-orig 8 1 0' \
  'nvfp4-a16-online-mxfp8 8 1 0'
```

Repeat with the 4.6.0 image and different `RESULT_ROOT`, `CACHE_A`, `CACHE_B`,
and `TMP_ROOT`. The validation runner starts both servers first and does not
send any benchmark request until both are healthy and the settle period ends.

Runtime package inspection is provided by
[`inspect-runtime.py`](cutlass-dsl-46-w4a16-regression-2026-07-18/inspect-runtime.py):

```bash
docker run --rm --entrypoint /opt/venv/bin/python \
  local/glm52-v19-cutlass453 \
  /dev/stdin < \
  models/glm5.2/cutlass-dsl-46-w4a16-regression-2026-07-18/inspect-runtime.py
```

For an affected cached object, inspect generated resources with:

```bash
/usr/local/cuda/bin/cuobjdump --dump-resource-usage /path/to/cute_compile/object.o
```

Objects containing the relevant signature can be located with:

```bash
find /cache/jit/b12x/cute_compile -type f -name '*.o' -print0 \
  | xargs -0 grep -a -l -m1 'W4A16FusedMoeKernel'
```

## Release Gate

Do not move the unified SM120 image back to CUTLASS DSL 4.6 or newer solely
because the upstream requirement changed. First rerun the same TP8/DCP1 A16
64k prefill comparison and inspect the generated W4A16 resource usage. A valid
upgrade must remove the stack spill and stay within normal run-to-run variance
of the current 4.5.3 baseline.
